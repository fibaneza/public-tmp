== What RAG Is

Retrieval-Augmented Generation puts a search engine in front of a language
model. Instead of asking the model to recall a fact from its weights, you
retrieve the passage that contains the fact and put it in the prompt.

That one change buys four things a fine-tuned model cannot give you:

[cols="1,3", options="header"]
|===
|Property |Why RAG gives it to you

|*Freshness*
|Update a document and the next query sees it. No retraining, no deployment.

|*Attribution*
|The answer points at a chunk, which points at a page. A user can check it.

|*Access control*
|Retrieval is a query you can filter. A model's weights cannot be filtered per-user.

|*Cost*
|Indexing a corpus costs cents. Fine-tuning on it costs orders of magnitude more,
 and has to be redone every time the corpus changes.
|===

What RAG does *not* fix: reasoning quality, arithmetic, or a corpus that does
not contain the answer. RAG changes what the model knows, not how well it thinks.

See also xref:../AI_guide.adoc[AI guide] for the surrounding concepts (embeddings,
quantization, fine-tuning vs RAG) and xref:RAG_Glossary.adoc[the glossary] for
terminology.

=== RAG vs Fine-tuning vs Long Context

The three are not competitors so much as answers to different questions.

[cols="1,2,2,2", options="header"]
|===
|
|RAG
|Fine-tuning
|Long context (stuff everything)

|Answers
|"What does the model *know*?"
|"How does the model *behave*?"
|"What is in front of it right now?"

|Update cost
|Seconds (re-index one doc)
|Hours to days (retrain)
|Free (change the prompt)

|Scales to
|Terabytes
|N/A
|~1-2M tokens, then it stops

|Attribution
|Native
|None
|Possible but weak

|Per-query cost
|Low (5 chunks in the prompt)
|Lowest
|Very high (whole corpus every time)

|Best for
|Facts, documents, policies, code
|Format, tone, domain jargon, structured output
|Small fixed corpora; a single long document
|===

They compose. The strongest production systems are usually RAG for knowledge,
a light fine-tune or a good system prompt for behaviour, and a long context
window used to fit *more retrieved chunks*, not to skip retrieval.

== The Naive Pipeline

Every RAG system starts here. It is worth writing down precisely, because each
advanced technique in xref:RAG_Techniques.adoc[the techniques document] is a
repair to one specific arrow.

[mermaid]
....
flowchart LR
    subgraph INDEX["Indexing — offline, once per document"]
        A[Documents<br/>PDF / HTML / MD] --> B[Parse<br/>extract text]
        B --> C[Chunk<br/>split into passages]
        C --> D[Embed<br/>text → vector]
        D --> E[(Vector Store<br/>HNSW / IVF)]
    end

    subgraph QUERY["Querying — online, every request"]
        Q[User question] --> QE[Embed query]
        QE --> S[ANN search<br/>top-k by cosine]
        E -.-> S
        S --> P[Build prompt<br/>context + question]
        P --> L[LLM]
        L --> ANS[Answer]
    end

    style INDEX fill:#e8f0fe,stroke:#4285f4
    style QUERY fill:#e6f4ea,stroke:#34a853
....

In code that is about fifteen lines — see
xref:examples/naive_rag.py[`examples/naive_rag.py`].

[source,python]
----
# The whole of naive RAG, compressed:
chunks   = split(document, size=500, overlap=50)
vectors  = embed(chunks)                       # offline
hits     = top_k(embed(question) @ vectors, k=3)   # online
answer   = llm(f"Context:\n{hits}\n\nQuestion: {question}")
----

=== Where It Breaks

Naive RAG works surprisingly well on a clean, small, homogeneous corpus, and
then fails in predictable ways as soon as reality arrives.

[cols="1,3,2", options="header"]
|===
|Stage |Failure |Repaired by

|Parse
|PDF text extracted in storage order — two-column papers interleaved, tables flattened into digit soup.
|xref:RAG_Chunking.adoc#_structure_aware_parsing[Structure-aware parsing (Docling)]

|Chunk
|A fact is cut across a boundary; neither half is retrievable.
|xref:RAG_Chunking.adoc[Overlap, recursive and semantic chunking]

|Chunk
|Chunk is precise enough to retrieve but too thin to answer from.
|xref:RAG_Techniques.adoc#_parent_child_retrieval[Parent-Child], sentence windows

|Chunk
|Chunk lost the context that made it meaningful ("revenue grew 3%" — whose?).
|xref:RAG_Techniques.adoc#_contextual_retrieval[Contextual Retrieval]

|Embed
|Rare tokens, IDs, acronyms and exact numbers blur into their neighbourhood.
|xref:RAG_Hybrid_Search.adoc[Hybrid search with BM25]

|Embed
|The question and its answer are different genres of text, so they embed apart.
|xref:RAG_Techniques.adoc#_hyde[HyDE]

|Search
|Top-k ordering is coarse; the right chunk sits at rank 8 and you passed 5.
|xref:RAG_Reranking.adoc[Cross-encoder reranking]

|Search
|One phrasing is one sample of intent; a different phrasing finds different chunks.
|xref:RAG_Techniques.adoc#_rag_fusion[RAG-Fusion], Multi-Query

|Search
|A follow-up ("what does it do?") embeds to noise.
|xref:RAG_Conversational_Memory.adoc[Query contextualisation]

|Prompt
|Ten chunks of which two are relevant; the answer drowns in the middle.
|xref:RAG_Techniques.adoc#_contextual_compression[Contextual compression]

|Generate
|Fluent answer, unsupported claim, no way for the user to tell.
|xref:RAG_Citations.adoc[Cited claims + verification]

|Everything
|You changed something and have no idea whether it helped.
|xref:RAG_Evaluation.adoc[RAGAS and retrieval metrics]
|===

== The Production Pipeline

Stack the repairs and you get the architecture most serious systems converge on.
The ordering is not arbitrary — see the note below the diagram.

[mermaid]
....
flowchart TB
    subgraph ING["① Ingestion"]
        direction LR
        I1[Docling<br/>layout parse] --> I2[Structural<br/>chunking]
        I2 --> I3[Contextual<br/>preamble via LLM]
        I3 --> I4[Embed] --> I5[(Vector index)]
        I3 --> I6[Tokenize] --> I7[(BM25 index)]
        I3 --> I8[(Doc metadata<br/>doc_id, page, ACL)]
    end

    subgraph UND["② Query understanding"]
        direction LR
        U1[Contextualise<br/>follow-up] --> U2[Rewrite /<br/>decompose]
        U2 --> U3[Multi-query<br/>expansion]
    end

    subgraph RET["③ Retrieval — recall"]
        direction LR
        R1[Dense<br/>ANN search] --> R3{{RRF merge}}
        R2[BM25<br/>lexical search] --> R3
        R3 --> R4[~50 candidates]
    end

    subgraph RANK["④ Ranking — precision"]
        direction LR
        K1[Cross-encoder<br/>rerank] --> K2[Parent<br/>expansion]
        K2 --> K3[Contextual<br/>compression]
        K3 --> K4[~5 chunks]
    end

    subgraph GEN["⑤ Generation"]
        direction LR
        G1[Prompt with<br/>numbered sources] --> G2[LLM]
        G2 --> G3[Cited claims<br/>JSON]
        G3 --> G4[Verify quotes]
    end

    ING -.->|indexes| RET
    Q([User question]) --> UND --> RET --> RANK --> GEN --> A([Cited answer])
    GEN -.->|trace| EV[(Eval log<br/>RAGAS)]

    style ING fill:#e8f0fe,stroke:#4285f4
    style UND fill:#fef7e0,stroke:#fbbc04
    style RET fill:#e6f4ea,stroke:#34a853
    style RANK fill:#fce8e6,stroke:#ea4335
    style GEN fill:#f3e8fd,stroke:#a142f4
....

*Why this order:*

. *Cheap and broad before expensive and narrow.* Hybrid retrieval touches every
  chunk in the corpus but costs microseconds each. The cross-encoder costs
  milliseconds each, so it only sees 50. The LLM costs hundreds of milliseconds,
  so it sees 5. Invert any of those and you pay orders of magnitude more for the
  same answer.
. *Rerank before compressing.* Compression is per-chunk work. Doing it on 50
  candidates when 45 will be discarded is pure waste.
. *Expand to parents after reranking.* The reranker scores best on precise,
  focused text; the LLM answers best with surrounding context. Give each the
  input it is good at.
. *Verify after generating.* Citation verification is the only stage that can
  catch a confidently wrong answer, and it needs an answer to check.

The wired-together implementation with per-stage ablation flags is
xref:examples/production_rag_pipeline.py[`examples/production_rag_pipeline.py`].

== What to Build First

Techniques are not equally valuable. Measured across a lot of published
ablations and practitioner reports, the rough order of return on effort:

[cols="1,2,1,1,3", options="header"]
|===
|# |Technique |Impact |Effort |Notes

|1
|xref:RAG_Chunking.adoc[Better chunking]
|High
|Low
|Structure-aware splitting fixes problems no downstream stage can. Do this first.

|2
|xref:RAG_Hybrid_Search.adoc[Hybrid search]
|High
|Low
|BM25 + RRF is ~30 lines and covers dense search's blind spot for IDs and acronyms.

|3
|xref:RAG_Reranking.adoc[Cross-encoder reranking]
|Very high
|Low
|Single biggest accuracy jump per line of code. +10-25 nDCG@5 is typical.

|4
|xref:RAG_Evaluation.adoc[An eval set]
|Critical
|Medium
|Not an accuracy win — it is what tells you whether 1-3 helped. Build it by step 4 at the latest.

|5
|xref:RAG_Citations.adoc[Citations]
|High (trust)
|Low
|Does not change accuracy; changes whether anyone can act on the answer.

|6
|xref:RAG_Techniques.adoc#_contextual_retrieval[Contextual Retrieval]
|High
|Medium
|Index-time LLM cost, big recall win. Needs prompt caching to be affordable.

|7
|xref:RAG_Conversational_Memory.adoc[Conversational memory]
|High (UX)
|Low
|Turn 2 is broken without it. Users notice immediately.

|8
|xref:RAG_Techniques.adoc#_parent_child_retrieval[Parent-Child]
|Medium
|Medium
|Resolves the chunk-size trade-off rather than tuning it.

|9
|xref:RAG_Techniques.adoc#_rag_fusion[RAG-Fusion / Multi-Query]
|Medium
|Low
|Costs an LLM call and 3x retrieval latency. Measure before shipping.

|10
|xref:RAG_Architectures.adoc#_agentic_rag[Agentic RAG]
|High, variable
|High
|Necessary for multi-hop and comparison questions; unpredictable latency and cost.
|===

The one non-negotiable: *do not skip step 4*. Without an eval set every later
decision is a guess dressed as an opinion.
